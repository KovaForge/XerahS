## medium: Active-window capture falls back to interactive region selection on wlroots desktops

id: fnd_sig-feat-library-057839b894-95c9_b127dbe5e6
category: api-contract
confidence: high
triage: contract-mismatch
status: open
feature: C# source src/platform/XerahS.Platform.Linux/Capture/Wayland (feat_library_057839b894)

evidence:
- src/platform/XerahS.Platform.Linux/Capture/Wayland/WaylandCliCapture.cs:176-188 (CaptureActiveWindowAsync)
- src/platform/XerahS.Platform.Linux/Capture/Wayland/WaylandCliCapture.cs:218-255 (CaptureWithGrimSlurpAsync)

When LinuxCaptureKind.ActiveWindow is requested, non-Hyprland wlroots desktops and null desktop route to CaptureWithGrimSlurpAsync. That helper starts slurp and waits for user-selected geometry, then captures that region with grim. This does not implement the active-window contract and can silently return a user-selected region instead of the focused window.

recommendation:
Do not use grim+slurp as an active-window fallback. Return null for unsupported desktops, or add a real active-window implementation for each supported compositor, such as swaymsg/jq focused container geometry for Sway or a compositor-specific helper.

test analysis:
The included tests are assistant/history/Avalonia tests and do not exercise WaylandCliCapture or LinuxCaptureKind.ActiveWindow behavior.

suggested regression test:
Add a WaylandCliCapture test seam around process invocation and assert that ActiveWindow on SWAY does not invoke slurp/region selection, or that it invokes a compositor-specific active-window command.

minimum fix scope:
Change CaptureActiveWindowAsync routing for wlroots/null desktops and add focused coverage for active-window fallback behavior.

## medium: FileDownloader can hang forever when the response stream ends early

id: fnd_sig-feat-library-0584088912-a106_7dcb6d85a5
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: C# source src/desktop/core/XerahS.Common#2 (feat_library_0584088912)

evidence:
- src/desktop/core/XerahS.Common/FileDownloader.cs:112-124 (FileDownloader.DoWork)
- src/desktop/core/XerahS.Common/FileDownloader.cs:136-140 (FileDownloader.DoWork)

The download loop continues while DownloadedSize is less than FileSize, but it never checks for ReadAsync returning 0. If the server closes the connection before the declared Content-Length is reached, bytesRead stays 0, DownloadedSize never advances, IsCanceled remains false, and the loop spins indefinitely while repeatedly writing zero bytes.

recommendation:
Break or throw when bytesRead is 0 before DownloadedSize reaches FileSize, and treat the download as failed unless the expected length was reached.

test analysis:
No tests were included for truncated HTTP responses or premature EOF behavior.

suggested regression test:
Add a downloader test using a local test server that advertises a larger Content-Length than it sends and assert StartDownload completes with failure instead of hanging.

minimum fix scope:
Update FileDownloader.DoWork loop EOF handling and add a regression test.

repro:
Serve a response with Content-Length larger than the actual body, then call StartDownload. Once the stream reaches EOF, ReadAsync returns 0 and the loop never exits.

## medium: HSB equality ignores alpha while hash code includes it

id: fnd_sig-feat-library-0584088912-15bf_078d713cef
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: C# source src/desktop/core/XerahS.Common#2 (feat_library_0584088912)

evidence:
- src/desktop/core/XerahS.Common/HSB.cs:163-166 (HSB.operator ==)
- src/desktop/core/XerahS.Common/HSB.cs:183-190 (HSB.GetHashCode/Equals)

Equals delegates to the == operator, which compares Hue, Saturation, and Brightness but not Alpha. GetHashCode includes Alpha. Two HSB values that differ only by alpha therefore compare equal but can produce different hash codes, breaking the .NET equality/hash contract for HashSet, Dictionary keys, LINQ Distinct, and other hashed collections.

recommendation:
Include Alpha in the == comparison, or remove Alpha from GetHashCode if alpha is intentionally excluded from equality. Keep Equals, ==, !=, and GetHashCode semantically aligned.

test analysis:
No tests were included for HSB equality or hashed collection behavior.

suggested regression test:
Add a unit test asserting that HSB values differing only by Alpha are either not equal and have distinct semantics, or are equal and produce the same hash code, depending on the intended contract.

minimum fix scope:
Update HSB equality and corresponding tests.

repro:
Create new HSB(0.1, 0.2, 0.3, 10) and new HSB(0.1, 0.2, 0.3, 20). Equals returns true, but GetHashCode can differ.

## medium: Redirected stderr can block CLI capture helpers before timeout

id: fnd_sig-feat-library-057839b894-d588_9212997b0c
category: performance
confidence: medium
triage: risk
status: open
feature: C# source src/platform/XerahS.Platform.Linux/Capture/Wayland (feat_library_057839b894)

evidence:
- src/platform/XerahS.Platform.Linux/Capture/Wayland/WaylandCliCapture.cs:70-97 (SelectRegionWithSlurpAsync)
- src/platform/XerahS.Platform.Linux/Capture/Wayland/WaylandCliCapture.cs:224-237 (CaptureWithGrimSlurpAsync)
- src/platform/XerahS.Platform.Linux/Capture/Wayland/WaylandCliCapture.cs:402-417 (CaptureWithGrimAsync)

The helpers redirect StandardError but wait for process exit before reading or draining it, and most helpers never read it at all. If grim, slurp, spectacle, gnome-screenshot, grimblast, or hyprshot emits enough diagnostics to fill the redirected pipe, the child process can block and the capture will hang until the hard timeout, even when the command otherwise completed or failed quickly.

recommendation:
Either do not redirect stderr when it is unused, or drain stdout/stderr asynchronously while the process runs. Prefer WaitForExitAsync with cancellation and concurrent ReadToEndAsync tasks so command output cannot backpressure the child process.

test analysis:
The included tests do not cover Wayland CLI process execution, stderr-heavy failures, or timeout behavior.

suggested regression test:
Add a process-runner abstraction and a test fake that writes large stderr output before exit; assert capture returns promptly and logs/handles the failure without waiting for the timeout.

minimum fix scope:
Update the shared process execution pattern in WaylandCliCapture so all redirected streams are drained or unused redirects are removed.

## low: String conversion silently erases unsupported collection values

id: fnd_sig-feat-library-007bd09216-5c05_d3f2e07f89

status: open

- src/desktop/core/XerahS.Common/UITypeEditors/StringCollectionToStringTypeConverter.cs:33-45 (StringCollectionToStringTypeConverter.ConvertTo)

The converter handles destinationType string by returning a joined value only when the input is exactly List<string>; every other value type, including other common string collection types or an accidental unsupported value, is converted to string.Empty instead of delegating to the base converter or reporting the unsupported conversion. recommendation:
Only return string.Empty for an intentionally empty or null value if that is the desired contract. For unsupported non-null values, delegate to base.ConvertTo or support broader collection interfaces such as IEnumerable<string> while excluding string itself.

test analysis:
No linked tests were included for StringCollectionToStringTypeConverter behavior or unsupported input handling.

suggested regression test:
Add converter tests for List<string>, null, string[], Collection<string>, and an unsupported non-null value to lock in the intended conversion contract.

minimum fix scope:
Update StringCollectionToStringTypeConverter.ConvertTo and add focused unit coverage for supported and unsupported inputs.
